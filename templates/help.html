Flex Router 策略说明

Flex Router 是本机的 OpenAI 兼容路由层。调用方只需选择稳定的模型或池名称；通道、额度、重试与退让策略都由 Router 统一管理。

它为调用方增加了什么

Hermes / OpenCode→稳定模型或池名称→Flex Router→多个上游通道

上游渠道可以变化、故障或额度受限，而调用方配置保持不变。Router 负责在合适的通道上完成调用，并保留完整的运行证据。

池化与固定模型

一个对外模型可以映射到多个通道，也可以直连一个指定 Channel。

  • 池按成本、优先级和通道健康度选择。
  • 固定模型适合需要稳定验证或排障的场景。
  • 通道可使用不同模型，只要能力和上下文满足请求。

额度与限流保护

Router 记录每个通道的调用，管理 5 小时配额，并从真实 429 中学习。

  • RPM / TPM 只在上游真实限流后退让。
  • 指数退避避免持续撞限。
  • 额度或冷却中的通道不会被再次选中。

重试、退让与长任务

普通错误按通道策略重试；池中有备用通道时可退让。

  • 默认池在 6 / 12 分钟无响应对象或 SSE 活动时启动副本；单次尝试提前触发安全超时，也会立即推进下一阶段。
  • 同一 Channel 已有未完成请求时，后续 Hedge 会跳过它，避免重复占用上游 RPM。
  • 每次 LiteLLM 调用默认 180 秒无响应对象或 180 秒无首 SSE 就记为超时；15 分钟仍无首活动则返回 504。
  • 配置了 selection.hedge.stages 的 Pool 按 YAML 中的阶段顺序向指定 Channel 发副本。

会话连续性

Router 可根据对话内容变化和空闲时间维持通道亲和性。

  • 同一段连续对话尽量不切换模型。
  • 长时间空闲或上下文明显变化后，可重新选择更合适的通道。
  • 减少不同模型切换导致的风格与工具行为波动。

退让策略时间表

下表只在 Router 收到相应的真实上游错误或满足明确条件时触发；不会预先猜测限流，也不会对普通参数错误盲目重试。

触发条件同一原请求的处理其它新请求
RPM / TPM 429指数退避：每次等待时间翻倍，直到 Setup 中 RPM / TPM 的累计等待上限。该通道进入冷却；池内可用备用通道仍可使用。
allocated quota exceeded固定回原 Channel 验证：1、2、4 分钟；仍失败则每 10 分钟一次。疑似/确认配额异常的 Channel 不参与正常选路。
engine is not available temporarily固定回原 Channel 验证：15、45、120 秒；仍失败则每 5 分钟一次。该 Channel 暂不参与正常选路。
本地五小时额度达到保护阈值固定回原 Channel：1、5、10、20 分钟；之后每 30 分钟验证。新请求继续受本地保护，不会并发冲击该 Channel。
上游无首活动每次尝试默认 180 秒响应对象 / 180 秒首 SSE 超时，超时会推进下一 Hedge 阶段；默认池 6 / 12 分钟 Hedge；配置了 Hedge 阶段的 Pool 按各阶段 Channel 执行；15 分钟返回 504。同一 Channel 不重复并发；任意副本先有响应或 SSE 即获胜。
完全相同的短时重发仅非流式、无工具调用：120 秒内回放上次完整成功 JSON，不再访问上游。匹配调用方、模型和整份请求的本机 HMAC 指纹；流式、工具、失败或截断结果不回放。
其它 HTTP 400视为请求/参数问题，直接返回，不自动重试。避免用重试掩盖模型名、工具格式或参数错误。

池策略名称

CONFIG 中每个 POOL 都会显示当前实际策略的中文名称：

策略名称含义
配置驱动多阶段 HedgePool 通过 selection.hedge.stages 指定各阶段的等待时间和目标 Channel。
轮转均衡 + 同通道 Hedge按轮转分配 Channel；无显式阶段配置时使用默认同 Channel Hedge。
成本优先 + 故障回退按 tier 优先使用低成本 Channel；配额、限流或故障时切换备用 Channel。
配额节奏优先 + 故障回退根据配额消耗节奏安排 Channel，异常时依次回退。

Hedge 的阶段顺序由 Pool 配置中的 selection.hedge.stages 决定：第一项先发，第二项后发；修改 YAML 后重启核心即可生效。

长任务、取消与可见证据

  • 首活动包含上游响应对象或任一 SSE 协议事件，不只是普通文本 token；一旦已有上游活动，不会因为生成慢而 Hedge。
  • watchdog 交接：响应对象选定后，监控从响应对象阶段交接到首 SSE 阶段，避免旧回调在 6 / 12 分钟重复派发同一请求。
  • 流式消费证据：Trace 会分别记录流式消费是否开始、首 SSE 等待是否开始，便于区分下游没有读取响应与上游没有发首事件。
  • 未进入流式消费：即使下游没有读取响应体，15 分钟首活动截止也由 watchdog 直接关闭 Trace，不会永久保持进行中；预响应 Hedge 阶段还会同步关闭未完成 attempt，不等待 SDK 清理。
  • 副本获胜后，Router 取消同一 Trace 中仍等待的旧副本；若上游不支持即时取消，可能仍产生上游费用，但不会再向调用方转发。
  • 调用方断开：在首字前或流式期间检测到真实 HTTP 断开时，Router 取消上游流和等待副本。标准 OpenAI 协议没有任务取消 ID，因此无法仅凭内容推断取消。
  • Trace会记录 LiteLLM task 启动、响应对象、首个 SSE、明确错误、超时、取消请求，以及 429、冷却、Hedge 和 TTFT。

短时结果恢复

对完全相同的 stream: false、无工具调用请求，Router 会在上次正常成功后的 120 秒 内直接恢复完整 JSON，并在 Trace 记录 replay_hit。它适合 Hermes 的命令批准类重发（例如已得到 APPROVE 但传输中断），不适用于流式内容或工具调用。完整响应仅短时保存在本机，到期删除；Prompt、API Key 和 Cookie 不会写入该临时表或长期统计。

可观测与管理

调用轨迹记录每次请求的选路、上游调用、429、冷却、重试、退让、首字时间、结果恢复和最终结果；默认不保存完整 Prompt。调用统计按 Channel 或 Pool 展示总请求、一次成功、重试后成功和真正失败，并提供小时趋势。管理页可测试、启停或重置单个通道。

Setup 中可单独开启全文上行请求留存，用于复现特定 payload：只保存实际发向上游的完整请求正文，不保存 API Header/Key，也不额外保存流式模型输出。默认关闭；保留时长、最多条数和最大空间可配，达到任一限制会从最旧记录自动清理。

边界与原则

Router 只负责路由与传输，不替代调用方的 Agent 决策。它不会把 API Key、Cookie 或完整对话内容写入调用轨迹；上游模型、额度与能力仍以配置和真实响应为准。
